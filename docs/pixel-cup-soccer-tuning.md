# Pixel Cup Soccer 핵심 수치 분석 (물리 · AI · 밸런스)

작성 2026-11-02 · 대상: `com.atoviamestudio.ixelupoccer19.apk`
목적: 독자 IP [골목컵 기획안](soccer-original-ip-plan.md)의 **튜닝 벤치마크**. 원작 수치를 그대로 옮기지 말고, 감각의 기준점과 비율로만 참고합니다.

## 0. 어떻게 얻었나, 얼마나 믿을 수 있나

| 출처 | 내용 | 신뢰도 |
|---|---|---|
| IL2CPP 메타데이터의 `const` 기본값 | 게임 코드 상수 8,419개 (float 2,828개, int 3,989개 등) | **관측값**: 빌드에 들어 있는 값 그대로 |
| `datapack.unity3d` TextAsset (XML) | 팀 356개 · 선수 6,410명 능력치, 포메이션, 경기장 바닥 물리, 대회 | **관측값** |
| 함수 디컴파일 (Ghidra, llvm-objdump) | 적분기, 능력치 공식, 난이도, 파울·카드·부상, 슛 방향, AI 노드 (7장) | **정적 확인**: 코드 경로는 확인했으나 실행 중 측정은 아님 |
| Mac에서 실행 중인 Ultimate 빌드 | 상수·데이터 비교, 저장된 설정 (8장) | **관측값** |

- 단위는 월드 좌표 픽셀(px)로 보입니다. 경기장 월드 크기는 3072 × 1740이고, 시간은 초 단위입니다.
- `static readonly` 값과 계산식(능력치 → 실제 속도 공식, AI 선택 확률 계산)은 네이티브 코드 안에 있어 아직 확인하지 못했습니다(→ 7장).
- 원본 덤프: [reference/pcs-gameplay-constants.txt](reference/pcs-gameplay-constants.txt)(경기 관련 상수 2,218줄), [reference/teams.txt](reference/teams.txt), [reference/formations.txt](reference/formations.txt), [reference/stadiumFloorTypes.txt](reference/stadiumFloorTypes.txt). 이 폴더는 `.gitignore`에 넣어 두었습니다(공개 저장소이므로).

**상태 배율 (`CPCSGameConstants`)**
- 포지션이 맞지 않으면 능력치 ×0.8, 부상 ×0.5, 물웅덩이 ×0.7, 쓰레기 ×0.8

## 5. AI

### 5.1 구조
- 결정 트리(`CAITreeNode`, `CAIMultipleDecision`, `CAISimpleChanceDecision`)에 판단 노드 약 30개가 달린 구조입니다.
- 공격: 공 몰고 달리기, 앞에 적이 있는지, 지쳤는지, 상대 골 근처인지 → 패스·슛·드리블·스프린트 결정
- 수비: 공에 가장 가까운 선수 압박, 블록·슬라이딩·정면 태클, 패스 가로채기, 수비 위치로 복귀
- 골키퍼: 공으로 달려나가기, 점프, 페널티 다이빙, 손에 공 잡기

### 5.2 판단 기준값
| 항목 | 값 |
|---|---|
| 상대 골문 근처 판단 거리 | 458 px |
| 칩킥 시도 최대 거리 | 458 px (X 400, Y 320) |
| 마크 없는 위치로 이동 최대 거리 | 150 px |
| 프리볼 슬라이딩 태클 최소 공 속도 | 250 px/s (킥 후 1초 이내) |
| 시야(LOS) 폭: 패스 (일반/지능형) | 40 / 60 px |
| 시야(LOS) 폭: 돌파 (일반/지능형) | 80 / 160 px |
| 근처 적 감지 거리 (일반/지능형) | 100 / 200 px |
| 포메이션 위치 허용 오차 | 50 px (전술 스킬이 있으면 15) |
| 버튼 입력 오차를 흉내 내는 값 | 0.1초 |

"지능형" 값은 전술 스킬(35–39번)이 있는 선수에게 적용되는 것으로 보입니다. **스킬이 AI의 인지 범위를 두 배로 늘리는 구조**입니다.

## 6. 밸런스 데이터

민첩, 속도, 가속, 정확도, 마킹, 드리블, 파워, 스태미나

**팀 등급별 평균** (팀 356개, 팀당 18명):
| 등급 | 팀 수 | 예시 | 평균 능력치 | 스태미나 |
|---|---|---|---|---|
| 0 | 16 | 레바논, 우즈베키스탄 | 약 0.49 | 0.49 |
| 1 | 140 | 나이지리아, 일본 | 약 0.54 | 0.74 |
| 2 | 50 | 멕시코, 잉글랜드 | 약 0.61 | 0.93 |

### 6.3 선수 유형 (커리어 성장 템플릿, `CPCSPlayerPotential`)
GK 3종(민첩형, 육중형, 균형형), DF 6종(공격형·수비형 풀백, 육중형·민첩형·공격형 센터백 등), MF 5종(수비형, 박스투박스, 공격형, 윙백, 균형형), FW 다수(육중형, 민첩형 등). 유형마다 능력치 8개의 성장 범위가 정해져 있습니다.
예) 육중형 센터백: 마킹 0.95–1.0, 스태미나 0.9–1.0, 속도 0.4–0.6, 드리블 0.2–0.4

### 6.4 스킬 45종
선수마다 45자리 0/1 문자열로 보유 여부를 저장합니다.

| 분류 | 스킬 |
|---|---|
| 공 다루기 | 볼 컨트롤, 가슴 트래핑, 볼 몰고 달리기, 스프린트, 드리블, 페이크 슛 |
| 수비 | 슬라이딩·블록·정면 태클, 점프/태클 회피, 패스 가로채기 |
| 패스 | 짧은·스루·로빙 패스, 크로스, 백힐 패스 |
| 슛 | 낮은·중간·강한·파워·칩·정밀·감아차기 슛, 골문 노린 킥, **슈퍼슛** |
| 공중볼 | 헤더(기본·공격·수비), 다이빙 헤더, 오버헤드킥, 시저킥 |
| 세트피스 | 코너킥, 프리킥, 페널티킥, 스로인 |

- 슈퍼슛·슈퍼세이브는 팀 단위 쿨다운 50초
- 스킬이 없으면 해당 동작 자체가 불가능한 경우가 많습니다(예: 오버헤드킥). 즉 **스킬 = 기술 해금** 구조입니다.

### 6.5 온라인 랭크
디비전 D → C → B → A → PCS → ELITE, 각 5단계. 포인트 1,049부터 2,499까지 50–100점 간격. 승리 시 최대 획득 포인트 D 40 → ELITE 10으로 상위로 갈수록 줄어듭니다.

## 7. 디컴파일로 확인한 로직

`libil2cpp.so`의 해당 함수를 Ghidra와 llvm-objdump로 디컴파일·디스어셈블해 확인했습니다. 정적 분석 결과이며, 실행 중 측정한 값은 아닙니다.

### 7.1 엔진 물리 적분 (`CGameObject.updateMovement`, 0x1838730)
모든 움직이는 개체(공, 선수, 심판, 장애물)가 같은 적분기를 씁니다.

```
dt     = Time.deltaTime × 경기속도배율          (CGame.Update)
accel  = accel + force × (1/질량)              (최대가속·최대힘으로 제한)
pos   += vel·dt + ½·accel·dt²
vel   += accel·dt
force  = 0
vel.xy *= powf(마찰XY, dt)                     (마찰 ≠ 1일 때)
```

- 마찰은 `vel.xy *= powf(마찰, dt[초])`로 적용됩니다(필드 `+0xcc`). 즉 **초당 잔존율**이며 프레임레이트와 무관합니다.
- 공 지면 마찰(`CPCSBall.setGroundFriction`)은 날씨로만 결정됩니다: 일반 0.965, 비 0.98, 눈 0.93. 땅에서 구르는 공은 1초에 3.5%만 느려집니다.
- 실측(7.6절)도 이를 뒷받침합니다. **공의 감속은 대부분 바운드할 때 계단식으로** 일어납니다(7.7절).
- 중력은 공 −320, 그 외 개체 −800(Z축)입니다.

### 7.2 능력치 → 실제 값 (`CPCSPlayer`)
| 값 | 공식 |
|---|---|
| 최고 속도 | `Lerp(0.5, 1.0, 에너지) × (부상 ? 0.5 : 1) × Lerp(205, 225, 속도S)` |
| 가속도 | `Lerp(0.5, 1.0, 에너지) × 부상 × Lerp(27000, 42000, 가속S)` |
| 회전 속도 | `Lerp(0.5, 1.0, 에너지) × 부상 × Lerp(720, 900, 민첩S)` |
| 볼 붙잡기 허용 속도 | `Lerp(0.9, 1.0, 에너지) × 부상 × Lerp(600, 1000, S)` (GK `Lerp(400, 600, S)`) |
| 스태미나 최대치 | `Lerp(0.5, 1.0, 에너지) × 부상 × Lerp(0.45, 0.7, 스태미나S) × 2382` |

여기서 실효 능력치 S는 다음과 같이 계산됩니다.
```
S = Clamp01( Clamp01(기본값 + 난이도가산) × 능력치배율 )
능력치배율 = 난이도배율 × 아드레날린(홈/원정, 막판, 점수차) × 사기 × 상황배율
          × (포지션 불일치 0.8) × (물웅덩이 0.7) × (쓰레기 0.8)
```

**난이도 배율 (`getDifficultyMultiplier`)** — 사람이 조작하는 팀과 CPU 팀에 서로 다르게 적용됩니다.
| 난이도 | 사람 팀 | CPU 팀 | CPU 능력치 가산 |
|---|---|---|---|
| 쉬움 | ×1.8 | ×0.6 | 0 |
| 보통 | ×1.25 | ×0.9 | 커리어 D디비전 +0.2 (GK +0.3) |
| 어려움 | ×0.9 (속도·마킹은 ×1.25, GK ×1.1) | ×1.15 | +0.3 (GK +0.4) |

→ **쉬움 모드에서는 내 팀이 CPU보다 3배 강한 능력치로 계산됩니다.** 능력치가 0–1로 잘리므로 실제 차이는 이보다 작습니다.

### 7.3 파울 · 카드 · 부상 판정 (`CPCSPlayer.calculateFoulChance`, 0x1559084)
태클이 상대에게 닿으면 세 가지 확률(%)을 정합니다.

**기본 확률표** (태클 종류별; 정면 블록은 스킬 유무로 나뉨)
| 표 | 상황 | 슬라이딩 | 블록 | 정면블록(스킬) | 정면블록 |
|---|---|---|---|---|---|
| 파울 | 상대 상태 A* | 10 | 25 | 20 | 50 |
| 파울 | 그 외 | 5 | 12 | 0 | 0 |
| 카드 | 상대 상태 A | 5 | 20 | 10 | 20 |
| 카드 | 그 외 | 2 | 10 | 0 | 0 |
| 부상 | 상대 상태 A | 2 | 30 | 5 | 10 |
| 부상 | 그 외 | 1 | 20 | 2 | 5 |

\* 상대 상태 A는 선수 플래그(`+0x688`)입니다. 공을 가진 상태로 추정되지만 확인하지 못했습니다.

**거리 가산표** (`ADDED_*`): 다른 분기에서는 공격자와 대상의 거리(50 이하 / 100 이하 / 그 이상)에 따라 아래 값을 더합니다.
| 거리 | 파울 | 카드 | 부상 |
|---|---|---|---|
| 100 초과 | 0 / 40 / 10 / 15 | 0 / 10 / 1 / 2 | 0 / 20 / 2 / 5 |
| 50–100 | 15 / 0 / 15 / 25 | 2 / 0 / 10 / 15 | 1 / 0 / 5 / 7 |
| 50 이하 | 20 / 0 / 50 / 65 | 5 / 0 / 15 / 25 | 2 / 0 / 7 / 10 |

**판정 순서**
1. 대상에게 특정 플래그(`+0x678`)가 있으면 세 확률에 +5
2. `Random(1–100) ≤ 카드확률` → 카드. 그중 **10%는 레드카드**
3. `Random(1–100) < 파울확률 × 설정배율` → 파울. 설정배율은 옵션 "파울 확률"(매우 낮음~매우 높음, 현재 저장값 2 = 보통)로 고르는 배열 값이고, 이 배열은 런타임에 채워져 정적으로는 확인하지 못했습니다.
4. 파울이고 대상이 부상 중이 아니면 `Random < 부상확률` → 부상. 경기 진행 조건(내부 값 > 7)이면 다시 10% 확률로 추가 효과
5. 골키퍼는 파울 대상에서 제외

### 7.4 슛 방향 (`calculateKickDir`, 0x1552fa0)
- **CPU**: 골문 양쪽 기둥 안쪽(기둥에서 20–45 px, 난이도별 `DISTANCE_POLE_*`)을 노립니다. 일반 선수는 50:50으로 고르고, 지능형 선수는 더 유리한 쪽 확률을 높입니다.
- **사람(킥 보조 ON)**: 바라보는 방향과 골문 중앙·위 기둥·아래 기둥 사이 각도를 계산해, **40° 이내면 가장 가까운 목표로 자동 보정**합니다. 그 밖에는 바라보는 방향 그대로 찹니다.
- 여기에 3장의 킥 종류별 오차 각도·속도 오차가 더해집니다.

### 7.5 AI 판단 노드 (`CAISimpleChanceDecision.evaluateAction`)
```
if (선수.행동가능(행동ID)) {
    평가 타임아웃 리셋
    return Random(1–100) ≤ 노드 확률
}
```
- 트리의 각 노드는 "가능 여부 확인 + 확률 주사위" 구조입니다. 평가 타임아웃이 있어 매 프레임 다시 판단하지 않습니다.
- 노드별 확률은 팀 성향(5.3절)과 플레이 스타일로 정해집니다(`setTeamPlayingStyleChanceValues`).
- 트리를 조립하는 `createAITrees`(0x14ea974)는 아직 디컴파일하지 않았습니다.

### 7.6 실측: 공 감속 (Mac Ultimate 빌드, 2026-11-02)
**방법**
- 실행 중인 게임 창을 3분 동안 녹화했습니다(`screencapture -V`, 56.8fps, 10,230프레임). 실제 친선 경기를 플레이한 장면입니다.
- HUD **미니맵**의 공 표식(회색 원 + 검은 테두리)을 프레임마다 추적했습니다. 미니맵은 카메라와 무관한 고정 축척이므로 카메라 보정이 필요 없습니다. 6,102프레임에서 검출했습니다.
- 미니맵 1px = 월드 12.4(가로) × 13.4(세로)입니다. 페널티 박스 458×825로 환산했습니다.
- 13프레임(0.23초) 이동 창으로 속도를 구했습니다.

**검증**: 측정된 킥 직후 속도 상위값(약 680–920)이 코드의 킥 힘 상수(XY 670–900)와 맞아, 좌표 환산이 타당함을 확인했습니다.

**결과 1 — 빠르게 움직이는 구간은 속도가 거의 일정**
선수 최고 속도(약 225–290)보다 빠르게 0.5–0.6초 이상 움직인 11개 구간의 시작→끝 속도입니다.

| 시점 | 시작 → 끝 | 비율 |
|---|---|---|
| 8.3초 | 467 → 447 | 0.96 |
| 19.8초 | 294 → 306 | 1.04 |
| 141.7초 | 489 → 476 | 0.97 |
| 143.6초 | 547 → 460 | 0.84 |
| 145.2초 | 334 → 327 | 0.98 |
| 165.9초 | 375 → 376 | 1.00 |
| 169.3초 | 323 → 299 | 0.93 |
| 170.1초 | 407 → 364 | 0.89 |

(4.9초, 24.8초, 69.9초 구간은 새로 찬 킥이 섞여 속도가 증가했습니다.)

| 모델 | 0.6초 뒤 예측 비율 | 판정 |
|---|---|---|
| `powf(0.965, dt[초])` — 코드 그대로 | 0.98 | ✔ 실측(0.84–1.04)과 일치 |
| 프레임당 0.965 (60fps) | 0.28 | ✗ |
| 연속 감속 k≈1.4/s | 0.43 | ✗ |

**결과 2 — 감속은 계단식**
킥 직후 감속처럼 보인 6구간의 감속 비율은 모두 **0.62–0.67**(723→449, 679→424, 722→485, 561→376, 814→518 등)이었습니다. 이는 일반 잔디의 바운드 XY 손실 0.65(약한 바운드)와 같은 값입니다. 바운드 한 번의 계단식 감속이 속도 평활화 때문에 연속 감속처럼 보였던 것입니다.

> 정정: 이 절의 이전 버전은 같은 데이터를 지수 감속으로 맞춰 "k≈1.4/s, 프레임당 마찰"이라고 결론 냈습니다. 일정 속도 구간 분석과 `CPCSBall` 디컴파일(7.7절)로 그 해석은 틀렸음을 확인했습니다.

**결론**
- 땅에서 구르는 공은 거의 감속하지 않습니다(초당 3.5%).
- 공이 느려지는 주된 원인은 **바운드할 때마다 30–60%씩 잃는 수평 속도**와 선수의 트래핑·태클입니다.
- 실제 경기에서 공이 고속으로 1초 이상 굴러간 구간은 없었습니다. 그 전에 거의 항상 누군가 공을 건드립니다.

**한계**
- 미니맵 1px ≈ 월드 12–13 단위라 순간 속도 잡음이 큽니다(±150). 바운드 계단을 프레임 단위로 직접 보지는 못했습니다.
- 공 높이를 알 수 없어 바운드 시점을 직접 확인하지 못했습니다. 바운드 비율이 일치한다는 점에서 추론한 것입니다.
- 녹화 당시 날씨와 바닥 종류를 확인하지 않았습니다.

### 7.7 공 바운드·지면 처리 (`CPCSBall.checkBouncing`, 0x1507378)
```
매 프레임 (게임 로직이 도는 상태일 때):
  if 공이 바닥에 닿고 vz < 0:                      // 바운드
      vz = −vz × 바닥.Z손실                         // 일반 잔디 0.67, 모래 0.5, 흙 0.75 …
      if |vz| ≥ 60:
          t = InverseLerp(60, 500, |vz|)
          vel.xy *= Lerp(바닥.XY손실min, 바닥.XY손실max, t)
                    // 일반 잔디: 약한 바운드 0.65 → 강한 바운드 0.40
      else:
          vz = 0                                    // 바운드 종료, 굴러가기 시작
  if 땅에 있음:  accelZ = 0,    마찰 = setGroundFriction()  (0.965 / 비 0.98 / 눈 0.93, 초당)
  else (공중):   accelZ = −320, 마찰 = 1.0 (감속 없음)
```

추가로 `CPCSBall.update`에서 땅에 있는 공에 **프레임마다** 곱해지는 배율이 있습니다. 이 값들은 dt를 쓰지 않으므로 프레임레이트에 따라 효과가 달라집니다.
| 조건 | X, Y | Z |
|---|---|---|
| 물웅덩이 위 | ×0.9 | ×0.95 |
| 쓰레기 위 | ×0.94 | ×0.97 |
| 펑크 난 공 | ×0.9 | ×0.5 |

→ 60fps에서 물웅덩이를 0.1초 지나면 속도가 약 0.53배가 됩니다. 사실상 "공을 멈추는 함정"입니다.

**골목컵 적용 제안**: 원작 구조(공중 무마찰 + 바운드 계단 감속 + 약한 지면 마찰)를 그대로 쓰면 원작과 비슷하게 공이 통통 튀며 굴러갑니다. 다만 원작은 지면 마찰이 매우 약해 굴러가는 패스가 멀리 갑니다. 5대5 좁은 경기장이라면 지면 마찰을 초당 0.5–0.7 정도로 강하게 하는 것을 검토할 만합니다. 장애물 배율은 dt 기반으로 바꿔 프레임레이트 의존을 없애야 합니다.

## 10. 골목컵에 적용할 때
1. **감각 기준점으로만 쓰기**: 원작 속도와 공 속도의 비율(선수 약 215 : 슛 700–900, 약 1 : 3.5–4)을 출발점으로 삼고, 5대5 세로 화면에 맞게 다시 튜닝합니다.
2. **가져올 설계 아이디어** (수치가 아닌 구조):
   - 차지 시간 하나로 킥 종류·세기·정확도·실축 위험까지 정하는 입력 설계
   - 바닥 종류 데이터로 물리를 바꾸는 구조 → 룰 카드 시스템의 기반
   - 지는 팀을 돕는 아드레날린 보정 (역전 재미)
   - 공 중력을 월드보다 약하게(−320 대 −800) 해서 공중볼을 읽기 쉽게
   - 스킬이 AI 인지 범위를 늘리는 구조 → 캐릭터 고유 기술과 연결
3. **바꿀 점**:
   - 원작은 능력치 차이가 작아 성장 체감이 약합니다. 골목컵은 레벨 상한 안에서 체감 차이를 더 크게 줍니다.
   - 모바일 한 손 조작에 맞게 차지 대신 **스와이프 길이**로 킥 세기를 정합니다.
4. 골목컵의 물리는 같은 구조(Euler 적분 + `powf(마찰, dt)` + 공중 무마찰 + 바운드 계단 손실)를 출발점으로 삼되, 5대5 세로 화면에 맞춰 수치를 새로 튜닝합니다(7.7절 제안 참고).
5. 난이도는 원작처럼 "내 팀 강화 + 상대 약화"를 함께 쓰는 방식이 체감 효과가 큽니다. 다만 쉬움 ×1.8처럼 극단적인 값은 피합니다.
